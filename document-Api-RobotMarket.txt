ROBOT MARKET ESP32 UI — FRONTEND API CONTRACT
==============================================

Document status: Development contract
Frontend entry points: index.html, app.html
Default API origin: Same origin as the UI
Local development proxy: http://192.168.1.118 (configured in vite.config.js)


1. PURPOSE AND SCOPE
--------------------

This document describes the HTTP and real-time interfaces expected by the
current Robot Market offline ESP32 frontend. It is based on calls that exist in
the source code, not on a hypothetical backend design.

Endpoints are marked as one of the following:

  ACTIVE       The production branch of the frontend currently calls it.
  MOCKED       The UI exists, but development mode serves local mock data.
  PLANNED      The call is present but commented out or not completed.

Development behavior is controlled by VITE_DEV_MODE. The development environment
sets it to true and loads mock-data.mjs; the production environment sets it to
false and uses the real application endpoints.


2. TRANSPORT AND COMMON RULES
-----------------------------

Protocol
  HTTP/1.1 is sufficient. HTTPS may be used when supported by the device.

Content type
  Request bodies use:

    Content-Type: application/json

  Unless explicitly documented otherwise, responses must use:

    Content-Type: application/json; charset=utf-8

Authentication
  Protected endpoints receive:

    Authorization: Bearer <token>

  The token is obtained from password or OTP authentication and stored by the
  browser as rm_token.

Common success envelope
  Mutation endpoints should return at least:

    {
      "success": true
    }

Common error envelope
  Errors should return a meaningful HTTP status and JSON body:

    {
      "success": false,
      "message": "Human-readable error",
      "code": "OPTIONAL_MACHINE_READABLE_CODE"
    }

Recommended status codes
  400  Invalid request or validation error
  401  Missing, invalid, or expired token
  403  Authenticated but not permitted
  404  Resource not found
  409  Conflicting device state
  422  Semantically invalid data
  429  Too many requests
  500  Internal device error
  503  Dependent hardware/service unavailable

Important frontend behavior
  A 401 response in app.html causes logout and redirects to index.html.
  All protected responses should be valid JSON, including errors.


3. AUTHENTICATION
-----------------

3.1 Password login [ACTIVE]

  POST /api/login
  Authentication: No

Request:

  {
    "username": "09123456789",
    "password": "admin123"
  }

Successful response:

  {
    "success": true,
    "token": "session-or-jwt-token",
    "role": "admin",
    "isFirstTime": false,
    "canRetry": true
  }

Supported roles used by the contract:
  admin, operator, viewer, factory

If isFirstTime is true, the frontend does not store the token. It stores the
username temporarily and displays the password-change view.

Failure example:

  HTTP 401
  {
    "success": false,
    "message": "Invalid username or password"
  }


3.2 Send login OTP [ACTIVE]

  POST /send-otp
  Authentication: No

Request:

  {
    "username": "09123456789"
  }

Successful response:

  {
    "success": true,
    "message": "OTP sent"
  }

The frontend validates Iranian mobile numbers with /^09\d{9}$/ before this
request. Rate limiting should return HTTP 429.


3.3 Verify login OTP [ACTIVE]

  POST /verify-otp
  Authentication: No

Request:

  {
    "code": "1234"
  }

Successful response:

  {
    "success": true,
    "token": "session-or-jwt-token",
    "role": "admin"
  }

The current UI requires a four-digit code. CAPTCHA is not sent by the current
implementation.


3.4 Change password [ACTIVE]

  POST /api/change-password
  Authentication: No for the first-login flow; firmware may additionally
                  permit an authenticated password-change flow.

Request:

  {
    "username": "09123456789",
    "oldPassword": "old-password",
    "newPassword": "new-password"
  }

Successful response:

  {
    "success": true,
    "token": "session-or-jwt-token"
  }

The frontend requires the new password to contain at least eight characters.


3.5 Hardware reset status [ACTIVE]

  GET /reset-status
  Authentication: No
  Response type: text/plain

Valid response bodies:

  waiting
  reset

The forgot-password screen polls this endpoint. "reset" returns the user to
the login screen; "waiting" keeps the countdown active.

5. NOTIFICATIONS AND REAL-TIME EVENTS
-------------------------------------

5.1 Server-sent events [ACTIVE]

  GET /api/realtime-updates
  Transport: text/event-stream
  Authentication: The browser EventSource API does not send the Bearer header.
                  Use the authenticated device session, a secure query token,
                  or same-origin cookie if authentication is required.

Each event data field must contain JSON. Supported payload fields include:

  {
    "notifications_count": 3,
    "notifications": [],
    "warnings": [],
    "latest_activity": []
  }

5.2 Notification list [EXPECTED BY UI DATA MODEL]

  GET /api/notifications
  Authentication: Yes

Response:

  {
    "notifications": [
      {
        "title": "Firmware updated",
        "message": "ESP firmware updated successfully",
        "status": "success",
        "time": "2026-07-15T09:00:00Z",
        "read": false
      }
    ]
  }

5.3 Mark all notifications as read [PLANNED]

  POST /api/notifications/read-all
  Authentication: Yes

Response: { "success": true }


6. CLIENTS
-----------

6.1 List clients [MOCKED / ACTIVE WHEN DEVELOPMENT MODE IS OFF]

  GET /api/clients
  Authentication: Yes

Response is an object keyed by a stable client key:

  {
    "client-1": {
      "id": "1001",
      "name": "Example Client",
      "status": "Active",
      "balance": 500000,
      "error": "",
      "disabledByServer": false
    }
  }

6.2 Create client [PLANNED]

  POST /api/clients
  Body: { "id": "1001", "name": "Example Client", "status": "Active" }

6.3 Replace client [PLANNED]

  PUT /api/clients/{key}
  Body: { "id": "1001", "name": "New name", "status": "Inactive" }

6.4 Delete client [PLANNED]

  DELETE /api/clients/{key}
  Response: { "success": true }

Create, update, and delete currently mutate browser mock state only.

12. FACTORY CONFIGURATION
-------------------------

12.1 Get factory configuration [MOCKED / ACTIVE WHEN DEVELOPMENT MODE IS OFF]

  GET /api/factory
  Authentication: Yes; factory role recommended

The response supplies network/DNS, system core, MQTT, and OTA form fields.

12.2 Save factory configuration [ACTIVE]

  POST /api/factory-save
  Authentication: Yes; factory role recommended

The request is created from factoryForm and includes at least:

  {
    "use_static": true,
    "mqtt_auto": true,
    "auth_code": "1234"
  }

Additional fields correspond to the form names for IP, DNS, MQTT, certificates,
OTA, and core settings.

Response: { "success": true }

12.3 Reset factory configuration [ACTIVE]

  POST /api/factory-reset
  Authentication: Yes; factory role recommended

Request:

  { "confirm": true }

Response:

  { "success": true, "rebooting": true }


13. LOG STREAM [PLANNED]
------------------------

  WebSocket /ws

The WebSocket implementation is currently commented out. Proposed server
messages are UTF-8 text lines or JSON objects containing timestamp, level, and
message. If token authentication is required, define a safe query-token or
initial authentication-message protocol before enabling this endpoint.


14. IMPLEMENTATION GAPS TO RESOLVE
----------------------------------

1. VITE_DEV_MODE=true bypasses real authentication and most GET endpoints.
2. Client create/update/delete calls are commented out.
3. Settings save returns a local { success: true } response.
4. Wi-Fi scan and connect calls are commented out.
5. Balance CSV export is not connected.
6. The WebSocket log stream is not enabled.
7. EventSource cannot attach the Authorization header used by normal requests.
8. API error responses should be standardized before firmware integration.
